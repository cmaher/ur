# ur-server (Server)

Long-running server process. Auto-spawned by `ur` on first use (not a launchd service). Listens on TCP via tonic gRPC, serves both host CLI (`ur`) and in-container workers (`ur-workertools` and `workerd` binaries). Depends on the `ur-postgres` container for database access — reads `DATABASE_URL` env var or falls back to `config.db.database_url()` (default: `postgres://ur:ur@ur-postgres:5432/ur`).

- Two gRPC servers: host server on `127.0.0.1:$server_port` (Core + Ticket, no auth) and worker server on `0.0.0.0:$worker_port` (HostExec + Ticket, auth interceptor validates worker-id/secret via WorkerManager)
- `CoreServiceHandler` is `Clone` — keep it stateless or use `Arc` for shared state
- Config and constants are in the `ur_config` crate, re-exported via `ur_server::config`
- `stream::spawn_child_output_stream` is the shared helper for streaming child process output as `CommandOutput` gRPC frames
- **All container and filesystem operations run on the host via builderd**, not inside the server container. The server container has no Docker socket or workspace filesystem access. `WorkerManager` delegates worker launch (`LaunchWorker` RPC) and stop (`StopWorker` RPC) to builderd's `BuilderContainerService`. `NetworkManager` uses the `InspectNetwork` RPC. `SquidManager` uses `ExecContainer` instead of a local `docker exec`. Pool slot operations go through `BuilderPoolService`: `RepoPoolManager` is a thin DB orchestrator that delegates all filesystem/git work (clone, reset, branch checkout) to `BuilderPoolClient` via five coarse-grained RPCs. The server never constructs git command strings for pool operations.
- **Slot ownership lives in the database** (ur-j5puq): `RepoPoolManager::acquire_slot(project, owner)` claims a slot by inserting the launch's `provisioning` row plus its `worker_slot` link in one transaction (`WorkerRepo::claim_slot`; `UNIQUE (slot_id)` decides races). There is no in-memory claim. `LaunchManager::launch` runs the whole launch on a spawned task so a dropped RPC cannot skip finalize or cleanup; an error before `run_and_record` deletes the claim row. Lifecycle transitions are compare-and-set in `WorkerRepo`: `finalize_worker_launch` (`provisioning → running`, the only transition to `running`; `false` means a stop landed mid-launch, and `WorkerManager::finish_launch` then stops the worker like a failed launch), `begin_stopping`, `finish_stop` (`stopping → stopped` + delete the link, only after builderd's Stop returned Ok, and never while the worker's own Launch RPC is unresolved: `worker.launch_pending`, migration 006, set by `record_provisioning_worker`; then only the launch path's `finish_launch_stop` or the startup pass, which clears every marker, may finish it). builderd's Stop is a per-worker barrier (it waits for or refuses that worker's launch), so any stopper may finish any stop, mid-launch included. **Identity is the worker id** (ur-ezhdb): builderd's Launch, Stop and List take and report worker ids only — never pass a container name, Docker ID or session name (sole exception: the upgrade-only `legacy_container_id`, see below). A container is named `NetworkConfig::worker_container_name(worker_id)` and labeled by builderd. Launch RPCs are never retried automatically (`ur_rpc::retry::NEVER_RETRIED`). Release is DB-only; the next acquire's `RecycleSlot` resets the slot.
- **Worker authentication exists before readiness**: `WorkerManager::run_and_record` records the `provisioning` worker row (refreshing a pool launch's claim row, inserting otherwise) with the generated secret before calling builderd's readiness-waiting `LaunchWorker`. Workerd needs that row to authenticate its initialization RPCs before its health endpoint starts. The row's `container_id` is the container name (`<worker_prefix><worker_id>`) or the session name, from `provisioning` on; a successful launch marks the row `running`; a failed launch is stopped like any worker (`abandon_launch` → `stop_by_worker_id`), leaving a `stopped` row (or `stopping` while builderd's Stop fails).
- Squid proxy: `SquidManager` writes config to `$UR_CONFIG/squid/` (`squid.conf` + `allowlist.txt`) and signals reconfigure via `ExecContainer` RPC → builderd. Compose manages the Squid container lifecycle — SquidManager only handles config files and reload signals.
- **Agent default resolution** (`WorkerModesConfig` in `worker.rs`): the floor for every built-in mode is no longer a hardcoded `AgentType::Claude` literal — `WorkerModesConfig::from_toml` reads the top-level `agent` key from the same `ur.toml` parse it already does for `[worker_modes]`/`[worker_models]` (via `ur_config::resolve_top_level_agent`) and threads it through `default_agents`, `seed_strategies`, `resolve_entry_agent`, and stores it on `default_agent` for `resolve_mode`'s fallback. Full precedence chain: `--agent` flag → `worker_modes.<mode>.agent` → top-level `agent` → claude. See `docs/codeflows/config.md#agent-default-precedence`.
- **Per-agent `[worker_models]` overrides** (`RawWorkerModels`/`RawStrategyDefaults` in `worker.rs`): every `[worker_models]` key is an agent table and each strategy is an inline `{ model, effort }` entry with independently optional fields. Flat strategy strings are rejected as a migration error. `WorkerModesConfig` keeps mode-level model and effort pins separately, then resolves both only after the final agent is known: mode field → `[worker_models.<agent>]` entry → the agent's built-in default. This prevents an explicit `--agent` launch override from inheriting defaults for the mode's original agent.
- **Credential gate before launch** (`check_credentials_seeded` in `grpc.rs`): once the agent is resolved, host-sourced agents fail with `CoreError::MissingCredentials` if their shared file is missing or a stub. `AgentAuth::allows_in_container_bootstrap` exempts AGY even though ur can seed its host OS-keyring credentials: an empty bind-mounted token file remains the fallback for first interactive sign-in. An agent with no auth profile is also exempt.
- **Local projects** (`local = true`, no `repo`): `ProjectRegistry::is_local(key)` is the server-side locality check. `RepoPoolManager::resolve_pool_project()` refuses local keys at the top of every pool entry point — before any DB query or builderd RPC, so a rejected launch leaves no half-prepared slot directory. `LaunchManager::reject_unsupported_local_launch` (decision in the free function `local_launch_rejection_reason`) permits only Manual strategy with a non-empty `workspace_dir`, returning `CoreError::LocalProjectUnsupportedLaunch` (`FailedPrecondition`) otherwise; it is the backstop for non-CLI callers (TUI, workerd). Context repos also reject local keys, since they mount a shared pool clone. Anything needing a git remote must go through `ProjectConfig::require_repo()`. See `docs/codeflows/config.md#local-projects`.
- **Worker runtime** (`ur_config::WorkerRuntime`): `LaunchManager::resolve_launch_runtime` resolves `--runtime` → `worker_modes.<mode>.runtime` → `projects.<key>.runtime` → top-level `runtime` → container, then `launch_runtime::validate_launch_runtime` rejects unusable `local` launches with `FailedPrecondition` before any slot or container work. The runtime is persisted on the worker row. See `docs/codeflows/config.md#runtime-precedence`.
- **Local launch/stop** (`local_launch.rs`, an `impl WorkerManager` block using its `pub(crate)` internals): `run_and_record` and `stop_by_worker_id` branch on the runtime. Local skips the credential gate, image resolution, NetworkManager and Squid env, and sends `BuilderLocalWorkerClient::launch_local_worker` a `LaunchLocalWorkerRequest` built from the same resolvers as the container path (`resolve_*`, `run_opts_builder::{resolve_mount_source, prepare_host_dir}`, `worker_skills`). Every path in it is a host path — never `/config`, `/workspace` or `/home/worker`. A failed launch is stopped via `abandon_launch` and returns builderd's error text; a failed stop leaves the row `stopping`. See `docs/codeflows/builderd.md#server-side`.
- **Worker reconciliation** (`worker_reconcile.rs`, `WorkerReconcileManager`): the DB says what should exist, builderd's lists (`ListLocalWorkers`, `ListWorkerContainers`) say what does, by worker id. `startup()` runs in `main.rs` before anything serves or dispatches (and before stale-row cleanup): every `provisioning` row of either runtime becomes `stopping`, then one pass. The loop runs a pass every 15s. One table for both runtimes: `running` + listed alive → none; `running` + absent or dead → stop path; `stopping` → stop path (retry); `provisioning` → none (periodic); listed with no active row (re-read first) → builderd Stop(worker_id); a list error → no change for that runtime. Read rows before the lists, and release a slot only via `stop_by_worker_id`, which requires builderd's Stop to succeed. A stop of a `stopped` row is a no-op. Upgrade limit: a pre-ur-ezhdb container (process-id name, no labels; its row recorded something other than the worker-id name: `worker::legacy_container_id`) is never listed, so its `running` row is left alone and only its row's stop path (which passes `legacy_container_id`, env-checked by builderd) stops it; a local `provisioning` row from before ur-j5puq has no slot link. Tests: `tests/local_launch_test.rs` (fake builderd; `table_*` tests cover the table for both runtimes).
- **Reaching a worker's daemon**: always go through the injected `WorkerdAddressResolver` (`address_for` / `client_for` / `tracked_client_for`) — never hand-build `http://<prefix><worker_id>:WORKERD_GRPC_PORT` (legacy containers keep `<prefix><process_id>`). Local workers resolve to builderd with an `ur-worker-id` routing header (`WorkerdClient::with_routing_worker_id`).
