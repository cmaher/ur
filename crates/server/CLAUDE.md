# ur-server (Server)

Long-running server process. Auto-spawned by `ur` on first use (not a launchd service). Listens on TCP via tonic gRPC, serves both host CLI (`ur`) and in-container workers (`workertools` and `workerd` binaries). Depends on the `ur-postgres` container for database access — reads `DATABASE_URL` env var or falls back to `config.db.database_url()` (default: `postgres://ur:ur@ur-postgres:5432/ur`).

- Two gRPC servers: host server on `127.0.0.1:$server_port` (Core + Ticket, no auth) and worker server on `0.0.0.0:$worker_port` (HostExec + Ticket, auth interceptor validates worker-id/secret via WorkerManager)
- `CoreServiceHandler` is `Clone` — keep it stateless or use `Arc` for shared state
- Config and constants are in the `ur_config` crate, re-exported via `ur_server::config`
- `stream::spawn_child_output_stream` is the shared helper for streaming child process output as `CommandOutput` gRPC frames
- **All container and filesystem operations run on the host via builderd**, not inside the server container. The server container has no Docker socket or workspace filesystem access. `WorkerManager` delegates worker launch (`LaunchWorker` RPC) and stop (`StopWorker` RPC) to builderd's `BuilderContainerService`. `NetworkManager` uses the `InspectNetwork` RPC. `SquidManager` uses `ExecContainer` instead of a local `docker exec`. Pool slot operations go through `BuilderPoolService`: `RepoPoolManager` is a thin DB orchestrator that delegates all filesystem/git work (clone, reset, clean, branch checkout) to `BuilderPoolClient` via six coarse-grained RPCs — the server never constructs git command strings for pool operations.
- Squid proxy: `SquidManager` writes config to `$UR_CONFIG/squid/` (`squid.conf` + `allowlist.txt`) and signals reconfigure via `ExecContainer` RPC → builderd. Compose manages the Squid container lifecycle — SquidManager only handles config files and reload signals.
- **Agent default resolution** (`WorkerModesConfig` in `worker.rs`): the floor for every built-in mode is no longer a hardcoded `AgentType::Claude` literal — `WorkerModesConfig::from_toml` reads the top-level `agent` key from the same `ur.toml` parse it already does for `[worker_modes]`/`[worker_models]` (via `ur_config::resolve_top_level_agent`) and threads it through `default_agents`, `seed_strategies`, `resolve_entry_agent`, and stores it on `default_agent` for `resolve_mode`'s fallback. Full precedence chain: `--agent` flag → `worker_modes.<mode>.agent` → top-level `agent` → claude. See `docs/codeflows/config.md#agent-default-precedence`.
- **Per-agent `[worker_models]` overrides** (`RawWorkerModels`/`RawStrategyModels` in `worker.rs`): `[worker_models]` mixes two value shapes under one TOML table — strategy keys (`code`/`design`/`manual`) map to a model string and apply to any agent, while agent-name keys (`[worker_models.<agent>]`) map to a nested table of the same three strategy keys and win only for that agent. `RawWorkerModels::from_value` classifies each key by its TOML value type (table → per-agent override, else → the flat table) rather than deserializing the section as one flat struct, since a single `#[derive(Deserialize)]` shape can't express "some values are strings, some are tables." Both the flat and per-agent tables use `deny_unknown_fields`, so a typo'd strategy key errors either way, and an unrecognized agent table name errors naming the valid agents. `WorkerModesConfig` stores the parsed `model_overrides` and only an explicit `worker_modes.<name>.model` per mode (`explicit_models`) — never a precomputed "resolved model" — because `resolve_mode` must compute the effective model *after* resolving the final agent (mode's own agent, or an explicit `--agent`/`requested_agent` override), not before: the two can differ, and computing the model too early bakes in the wrong agent's default. Full model resolution precedence, most specific first: custom mode's explicit `model` → `[worker_models.<agent>]` → `[worker_models]` → `agent.default_model(strategy)`.
- **Credential gate before launch** (`check_credentials_seeded` in `grpc.rs`): once the agent is resolved (`LaunchManager::launch`, right after `resolve_launch_workspace`), the launch fails with `CoreError::MissingCredentials` (`FailedPrecondition`, naming the agent and `AgentType::credentials_remediation()`) if that agent's host credentials file (`AgentType::host_credentials_path`, under `self.config_dir`) is missing or a stub — the shared `ur_config::credentials_file_is_seeded` / `MIN_SEEDED_CREDENTIALS_BYTES` predicate, so this gate and the CLI's own seeding checks cannot drift apart on the boundary. This exists because `RunOptsBuilder::add_credentials` calls `ensure_file_exists`, which *creates* an empty file so the bind mount succeeds — without this gate, a worker with no credentials boots straight into an interactive login prompt nobody sees. An agent with no auth profile (`agent.auth()` is `None`) is exempt. This check is deliberately stricter than the CLI's `ensure_credentials_for_all_agents`, which stays permissive (skip + warn — on `ur start` *and* on `ur worker launch`) so one agent's absent or broken host login isn't allowed to block a launch that resolves to a different, healthy agent — seeding on `ur start` is best-effort across every agent, but launching a *specific* agent with no credentials for it is a real, actionable failure.
- **Local projects** (`local = true`, no `repo`): `ProjectRegistry::is_local(key)` is the server-side locality check. `RepoPoolManager::resolve_pool_project()` refuses local keys at the top of every pool entry point — before any DB query or builderd RPC, so a rejected launch leaves no half-prepared slot directory. `LaunchManager::reject_unsupported_local_launch` (decision in the free function `local_launch_rejection_reason`) permits only Manual strategy with a non-empty `workspace_dir`, returning `CoreError::LocalProjectUnsupportedLaunch` (`FailedPrecondition`) otherwise; it is the backstop for non-CLI callers (TUI, workerd). Context repos also reject local keys, since they mount a shared pool clone. Anything needing a git remote must go through `ProjectConfig::require_repo()`. See `docs/codeflows/config.md#local-projects`.
